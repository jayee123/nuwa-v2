## 新增功能

### ① 重置試用

**位置**：後台 → 試用紀錄 → 每一列最右邊「重置試用」

點一次變成「確定重置 / 取消」，再點才真的送出（不用瀏覽器原生 modal，
它會卡住整個分頁）。刪掉之後該帳號就能重新試用這支 App。

**兩種用途**：

| | 場景 |
|---|---|
| 測試 | 測完把帳號還原成乾淨狀態，不必一直開新信箱 |
| 客服 | 使用者試用期間遇到系統問題沒用到，補一次給他 |

**權限：admin**（不限 superadmin）。這是要給第一線客服用的工具，
卡在 superadmin 等於沒人能用。代價由 audit log 承擔。

### ② 停用邀請碼

**位置**：後台 → 邀請碼 → 每一列最右邊「停用」（只有「可用」狀態的碼才顯示）

一樣是兩段式確認。停用後該碼立刻變成「已過期」，
使用者拿去兌換會看到「此邀請碼已過期，請向發送者索取新的邀請碼」。

**權限：superadmin**，比照同一頁的「產生」——能發碼的人才能殺碼。

## 實作細節與取捨

### 停用為什麼是「把到期日設成現在」

有兩個做法：

| | 做法 | 代價 |
|---|---|---|
| **A（採用）** | `expires_at = NOW()` | 狀態欄顯示「已過期」，看不出是自然到期還是被人作廢 |
| B | 新增 `disabled_at` 欄位 + 改 RPC + 新增「已停用」狀態 | 要再動一次兌換 RPC |

選 A 的理由：**不碰 `redeem_invite_for_app`**。那是存取權的關鍵路徑，
9/22 才剛修好過期檢查（migration 028）並在正式 DB 驗證過，
不值得為了狀態欄的語意再動一次。設成已過期就直接沿用已驗證的擋碼邏輯。

「誰、什麼時候停用的」記在 audit log，查得到。
之後真的需要在狀態欄分辨，B 案隨時可以補上，不急。

### 刪除前先撈快照

`user_app_trials` 刪掉就查不回來，所以 audit log 的 `detail` 存**整列內容**
（用戶、App、來源、當初兌換的碼、原到期日）。誤刪查得回原始資料。

### 併發保險

停用用的是 `UPDATE … WHERE used_by IS NULL`——停用的瞬間若剛好有人在兌換，
讓兌換勝出，不會出現「碼被停用了但試用也建了」的半套狀態。

## 已知限制

**1. 這兩支 API 沒有自動化測試**

專案現有的 49 條測試全是純函式（`launch-gate`、`phone`、`esafe`、`finance-stats`），
**沒有 API route 的測試骨架**。這兩支的邏輯幾乎都是 DB 呼叫，
要測就得先建整套 route 測試環境——那是新的基礎建設，不在這次範圍。

所以改走**手動驗證 + DB 端交叉查證**：畫面上看得到的（列消失、狀態轉換）由操作者確認，
畫面上看不到的（audit 快照、`UNIQUE` 是否釋放、`expires_at` 是不是真的設成當下）
由開發端直接查資料庫。結果見下一節。

**2. 停用是單向的，不可復原**

原本的到期日會被覆蓋（audit log 有記 `previous_expires_at`，但介面不做復原）。
需要的話重發一張，碼很便宜。

| audit 留下**刪除前**快照 | ✅ 八個欄位完整，含 `EXPIRE-TEST-082A78` 與原到期日 `2026-09-22T13:30` |

安全網是實的：就算誤刪，光憑 audit log 那筆快照就能原樣重建。

### ② 停用邀請碼

操作：發一張 `VERIFY-101019`，**有效天數填 0（不過期）**——故意選不過期的碼，
這樣「停用」就是唯一能讓它失效的原因，驗得乾淨。

```
07:18:34  產生 VERIFY-101019（expiresInDays: 0 → expires_at = null「不過期」）
07:18:55  expires_at 被設成這一刻
07:18:57  audit log 記下 invite.disable
```

| 驗證點 | 結果 |
|---|---|
| 狀態轉換 | ✅ 可用 → 已過期 |
| `used_by` | ✅ 仍是 `null`——停用**沒有**把碼消耗掉 |
| `expires_at` | ✅ 距操作當下 16 秒，確實是 `NOW()` |
| audit `previous_expires_at` | ✅ 記錄為 `null`（原本是「不過期」） |
| 操作者留痕 | ✅ `Admin` |

`previous_expires_at: null` 這筆特別有價值：這張碼原本永不過期，
唯一讓它失效的就是停用動作本身。

### ③ 第 00 階段自助

**不需要額外驗證——②本身就是實證。** 20 秒內就自製出一張
「已過期、未使用」的測試碼，正是 2026-09-21 那天做不到而卡在現場的事。

### 沒有測的一項，以及為什麼

「拿停用的碼去兌換，應顯示『此邀請碼已過期』」這一步**刻意跳過**。

理由：那條擋碼路徑 Steve 已在 2026-09-23 用 `EXPIRE-TEST-31551F` 實測過
（正確顯示已過期，且失敗後該碼在後台仍是「已過期」不是「已使用」）。
停用只是把 `expires_at` 設成現在，走的是**同一條已驗證的路徑**。

要重測就得把正式站切回封測、測完再還原——那正是封測清單第 10 段
點名的風險（「測完忘了還原，付費會員被擋一整夜」）。
用已有的證據換掉一次不必要的正式站狀態切換，是划算的。

## 第二輪（09-24）—— 回應〈給 Jeff — 2026-09-23〉

### ① 按鈕文案：使用者不知道自己燒掉了唯一一次試用

Steve 的觀察成立：按鈕寫「進入」，但在「門檻 ≥ 基本、使用者未達標、還沒試用過」
的 App 上，點下去那一瞬間就**永久**用掉他對這支 App 唯一一次的試用機會。

**但文案不能無條件改成「開始試用」。** 門檻設「不限方案」的 App（`planMeets` 恆真），
免費會員是直接進場、根本不開試用——寫「開始 14 天免費試用」就是另一個假訊息。

作法：卡片文案改接 `decideLaunch()`，與 gate 用**同一個判斷來源**：

| gate 回傳 | 按鈕文案 |
|---|---|
| `create_trial_and_enter` | **開始 N 天免費試用**（N 讀 `apps.trial_days`，不寫死） |
| `need_invite` | 我有邀請碼 |
| `go_subscribe` | 前往訂閱 |
| `enter` | 進入 |

附帶修掉一個既有不一致：以前卡片自己算一套，會出現「卡片說進入、點了卻被丟到訂閱頁」。

### ② 首頁有一行對使用者的假承諾（順手抓到）

首頁原本寫：

> 綁卡即享 **7 天**免費試用，之後**自動扣款**

**兩處都與事實相反**——天數是 14（且應讀 `apps.trial_days`），而定案的試用是
**免綁卡、不自動扣款**。這是承諾了系統不會做的事，正是 §4.6 說的
「會退費的那種誤導」。改成據實描述，且只在真的會開試用時才顯示。

### ③ 試用天數：真值收斂到公版

私版原本用 `trial_started_at + 寫死的 7 天` 自己推算到期日，公版 happy 設的是 14 天。

**這是一顆還沒發作的地雷**：一旦 `BILLING_ENFORCEMENT` 打開，第 8 天起
還在試用期內的人就會被私版擋掉。

改成讀公版 `user_app_trials.expires_at`（唯一真值）。讀不到才 fallback
本地推算，而且留 `console.warn`——比照 9/21 簡訊測試模式那次的教訓，
**沉默的 fallback 是下一次事故的溫床**。

### ④ 兩種「被擋下」的文案分開（§4.6）

| 情況 | 行為 | 訊息 |
|---|---|---|
| 額度用完 | 只擋 AI 對話，App 仍進得去 | 這個週期的 AI 對話次數已用完（N 則），升級到**進階**方案可以繼續使用 |
| 試用到期／方案不達標 | 擋在 App 門口 | 試用已結束，訂閱**基本**方案以上即可繼續使用 |

原文共用同一種語氣，還寫死「7 天」與「下月 1 號重置」——後者在 §4.4
改成訂閱週期起算日之後也會變錯，一併拿掉。

### ⑤ 重置試用權限收緊為 superadmin

原本設 admin，理由是「要給第一線客服用」。Steve 指出按破壞性排是反的：
重置會**永久刪一列**，停用碼重發就好。客服團隊還沒成形，那個前提現在不成立，
所以先從嚴。**等客服團隊真的建立後再放寬回 admin**（註解已寫在程式裡）。

## 🚨 上架 blocker：額度閘門目前是開的

§4.8 的疑慮**確認成立，而且是最壞情況**。

私版其實有完整的額度機制（`lib/billing/quotas.ts`、`usage_quotas` 表、
AI 呼叫前檢查），但：

```ts
export function isEnforcementEnabled(): boolean {
  return process.env.BILLING_ENFORCEMENT === 'true';
}
```

進正式站容器查過：**這個環境變數根本沒有設**。
`undefined === 'true'` → `false` → `checkQuotaAvailable` **永遠 allow**。

> **現在任何人註冊就能無限呼叫 AI**，不只是試用期間。

### 實際曝險（2026-09-24 查證）

| | |
|---|---|
| 歷史總呼叫 | 42 次（2026-07-28 ~ 09-10） |
| 累計成本 | NT$64.03 |
| 平均每次 | **NT$1.525**（每次約 15,000 input tokens） |
| 單人單月最高 | 28 次 / NT$31.71 |
| 現在打開開關會被擋的人 | **0 人** |

目前曝險趨近於零，因為封測只有 6 個人。**風險在單位成本 × 規模**：

```
試用者跑滿 trial 額度 100 次 × NT$1.525 ≈ NT$152／人
若照 §4.5 改讀基本方案（50 次）        ≈ NT$76／人
免費會員若照 §4.7 拿到 50 次／月       ≈ NT$76／月／人（持續，無收入）
```

**1000 個註冊者 = 試用期一次性 NT$76,000 ~ 152,000。**
列 blocker 的理由不是現在在燒錢，是**閘門是開的**。

### 不能只把開關打開

還有三個缺口會讓「打開」變成另一場事故：

1. **免費方案在兩邊都沒有定義**——公版 `plans` 表沒有 `free` 列、
   `users.dialog_limit` 是 0；私版 `PlanTier` 根本沒有 `free`，
   而 `market/plan.ts` 把公版 `free` **對映到私版 `trial`**。
   打開後免費會員會落到 trial tier 並套用試用到期檢查。
2. **`checkQuotaAvailable` 在 DB error 時 fail-open allow**——
   就算打開開關，DB 打嗝時閘門還是會開。
3. **兩套真相來源**（見下）。

## 第二批要先定案的兩個架構衝突

> **09-25 更新：已由 Jeff 拍板**（1A 存已用、2A 全平台一池），並已實作階段 1。見上方〈額度統一・階段 1〉。以下保留當初的分析。

這兩項不是寫程式的問題，是**規格與現況打架**，動手前要先有答案。

### 衝突 1：「存已用」vs 現有的「存剩餘」

§4.2 要求只存已用。但現在**同時有兩套**：

| 位置 | 存什麼 | |
|---|---|---|
| 公版 `users.dialog_limit` | **剩餘**（premium 三人是 200 / 198 / 136，在往下扣） | 正是 §4.2 明文否定的做法 |
| 私版 `happy.usage_quotas.messages_count` | **已用** | 符合 §4.2 |

照規格做就必須廢掉 `users.dialog_limit`。但公版註冊流程就會寫入它
（`dialog_limit: 0`），要先確認沒有別的地方在讀。**兩套真相來源不解決就會對不起來。**

### 衝突 2：「跨 App 共用一池」vs 額度表在 App 自己的 schema 裡

§4.3 要一個使用者一份總額度、依 App 分項。但 `usage_quotas` 在
**`happy` schema** 裡——這是**每支 App 各自一份**的設計，正好相反。

照規格做要把額度計量搬到公版、加上 App 歸屬欄位。**這是架構搬遷，不是加欄位。**
第二支 App 上線前一定要做完，否則兩支各記各的。

### 建議順序

```
（先定案衝突 1、2）
  1. 補免費方案的定義（公版 plans 加 free 列 + 私版 PlanTier 加 free）
  2. 廢 users.dialog_limit、統一到「存已用」
  3. 額度計量搬上公版、加 App 歸屬
  4. 重置時點改訂閱週期起算日（§4.4）
  5. 堵住 fail-open 的 DB error 路徑
  6. 最後才打開 BILLING_ENFORCEMENT
```
